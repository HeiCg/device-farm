    # `server/pipelines/` — MODULE.md

    ## Purpose

    The pipelines module owns CI-style multi-stage execution. A pipeline definition declares
    sequential stages (script + maestro), runs are scheduled via cron expressions or triggered
    via HTTP/manual invocation, and stage advancement is driven by a `job.completed` bus
    subscriber that joins `pipeline_stage_jobs` to identify which stages depend on a completed
    job. Phase 25 closed two migrations: (1) node-cron → boss.schedule (last node-cron consumer
    in the codebase), and (2) Promise-chain executeRun → bus subscriber stage advancement.

    ## Public API

    - `createPipelinesModule(deps)` — factory; returns `PipelinesModule` (MOD-06).
    - Back-compat classes (re-exported from internal/): `PipelineService`, `PipelineScheduler`,
      `PipelineBroadcaster`, `SecretsService`, `GitService`.
    - Events surface: `pipelinesRegistry`, `makePipelinesEmitters`, `PIPELINE_EVENT_NAMES`,
      `PipelineEventName`, `PIPELINE_RUN_AGGREGATE_ID`, 5 payload schemas + inferred types.
    - Queue surface: `PIPELINE_SCHEDULED_EXECUTE_QUEUE_NAME`, `registerPipelineScheduledExecuteQueue`,
      `registerPipelineScheduledExecuteWorker`, `upsertPipelineSchedule`, `removePipelineSchedule`,
      `pipelineScheduledExecutePayloadSchema`.

    ## Events Emitted

    | Name | Persisted (TRACE-08) | Aggregate Type | Payload |
    |------|----------------------|----------------|---------|
    | `pipeline.run.started` | false | pipeline-run | `{runId, pipelineId, triggerType}` |
    | `pipeline.stage.advanced` | false | pipeline-run | `{runId, stageIndex, stageName, status}` |
    | `pipeline.run.completed` | **true** | pipeline-run | `{runId, pipelineId, status, durationMs}` |
    | `pipeline.run.failed` | **true** | pipeline-run | `{runId, pipelineId, reason, failedStageIndex}` |
    | `pipeline.schedule.upserted` | false | pipeline-schedule | `{scheduleId, pipelineId, cron}` |

    ## Events Consumed

    - `job.completed` (from `server/jobs/`) — drives stage advancement via DB-driven join on
      `pipeline_stage_jobs.jobId`. NEVER routed via envelope correlationId (Pitfall 4).

    ## Queue Produced

    - `pipeline.scheduled.execute` (`PIPELINE_SCHEDULED_EXECUTE_QUEUE_NAME`) — created via
      `boss.createQueue` with `policy:'standard'` + `retryLimit:0`. Per-`pipelineSchedules.id`
      schedules upserted via `boss.schedule(name, cron, data, {key: scheduleId, tz: 'UTC'})`.

    ## Queue Consumed

    - `pipeline.scheduled.execute` (self-consumed) — worker invokes
      `service.triggerRun(pipelineId, 'schedule', variables)` and updates
      `pipelineSchedules.lastRunAt`.

    ## Invariants

       N-of-N gate). Tested by `__tests__/subscriber.spec.ts -t "matrix"`.

       deleting the row (Pitfall 3). Tested by `__tests__/queue.spec.ts -t "unschedule on delete"`.
    4. `scheduler.reconcileSchedules()` is idempotent on every boot (Pitfall 6 — pgboss.schedule
       converges to `pipelineSchedules` enabled rows). Tested by
       `__tests__/queue.spec.ts -t "idempotent upsert"`.
    5. ZERO `node-cron` imports anywhere in `server/`. Tested by
       `__tests__/lifecycle-ownership.spec.ts -t "zero node-cron"`.

    - Pipeline DAG / parallel stages (DEFERRED-25-B; v2 territory).

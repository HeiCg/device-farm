# Phase 21: Artifacts Module - Context

**Gathered:** 2026-04-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor `server/artifacts/` into the canonical module shape (MODULE.md + barrel `index.ts` + `events.ts` + `queue.ts` + tests-as-spec) and invert its trigger surface: recording/screenshot/memory artifact rows are created in reaction to `job.*` bus events, not via imperative calls from `jobs/job-service.ts`. All existing capabilities (scrcpy-based and adb-screenrecord-fallback recording, screenshot capture, memory snapshot) remain available; only the wiring changes.

</domain>

<decisions>
## Implementation Decisions

### Claude's Discretion

All implementation choices are at Claude's discretion — pure infrastructure phase. Planner follows the Phase 16/18/19/20 module template verbatim:

- **Module contract**: Copy the 9-section MODULE.md shape from `server/pool/MODULE.md` (the most recently canonicalized reference).
- **Events surface**: `artifact.created`, `recording.started`, `recording.stopped` per ROADMAP success criterion 2. Persistence flags follow the Phase 20 pattern (terminal/notable events persisted; transient lifecycle events not persisted) — specific choice deferred to planner.
- **Queue**: `recording.upload` with `singletonKey: recordingId` per success criterion 2; pg-boss wrapper from Phase 18.
- **Idempotency**: DB unique constraint + pre-check on `recordingId` (success criterion 3); exact constraint surface (composite vs. simple unique) deferred to planner based on current `artifacts` schema.
- **Subscriber wiring**: artifacts module subscribes to `job.started` (→ start recording/screenshot/memory capture) and `job.completed` (→ stop capture, create artifact rows). Zero direct calls from `jobs/*` into artifact services.
- **Tests**: tests-as-spec style matching Phase 16/20 — per-service `.spec.ts` with behaviour rows, DB-gated integration specs for subscriber + queue idempotency.

</decisions>

### Module files MISSING (to be created)

- `server/artifacts/MODULE.md` — 9-section contract.

### Reference implementations to copy from

- `server/pool/` — most recently canonicalized reference (Phase 20 close). Uses publisher-only stance, 4-event surface, `pool.*` bus, persisted side-channel.
- `server/hooks/` — Phase 16 pilot; reference for the createXxxModule factory + bus/queue wiring.
- `server/reporting/` — Phase 19; reference for queue worker with retry + DLQ idempotency pattern.
- `server/lifecycle/` — Phase 18; reference for `boss.schedule()` pattern (not directly needed here, but correlationId `boss.send()` wrapper is).

### Integration points to sever

- `server/jobs/job-service.ts` — current imperative callsites into recording/screenshot/memory services. Must be zero by end of phase (success criterion 1).
- Any `artifactService.persistArtifact(...)` or `recordingService.start(...)` calls in `server/jobs/*` need to become `bus.emit('job.started', ...)` producers instead, with the artifact module's subscribers reacting.

### Established conventions (from Phase 16/18/19/20)

- `MODULE.md` has exactly 9 H2 sections in fixed order (Purpose / Public API / Events Emitted / Events Consumed / Queue Produced / Queue Consumed / Invariants / Non-Goals / Dependencies).
- Events registered via `hooksRegistry`-style `typedBus()` pattern; emit helpers generated by `makeXxxEmitters()`.
- Queue names in `server/queue/names.ts` constant; worker wired in `registerXxxWorker(app)`.
- Tests-as-spec: behaviour rows in describe blocks with `[Invariant X]` tags referencing MODULE.md invariants.
- Nyquist baseline gate (coverage delta ≤ −2pp) per Phase 15-09.

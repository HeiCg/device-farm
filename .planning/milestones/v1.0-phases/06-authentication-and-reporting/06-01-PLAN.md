  <behavior>
    - generateKey() returns { raw, hash, salt, prefix } where raw starts with "df_", hash and salt are hex strings, prefix is first 8 chars of raw
    - validateKey(raw) returns true when key exists in mock DB and is not revoked/expired
    - validateKey(raw) returns false for revoked key
    - validateKey(raw) returns false for expired key
    - validateKey(raw) returns false for non-existent key
    - createKey(name) inserts into DB and returns { id, name, rawKey, prefix, createdAt }
    - listKeys() returns keys WITHOUT hash/salt, WITH prefix/name/timestamps
    - revokeKey(id) sets revoked=true
    - revokeKey(nonExistentId) throws error
  </behavior>
  <action>
    1. Add `apiKeys` table to server/db/schema.ts following existing pgTable pattern:
       - id: uuid PK with gen_random_uuid()
       - name: varchar(255) NOT NULL
       - keyHash: varchar(255) NOT NULL
       - keySalt: varchar(64) NOT NULL
       - keyPrefix: varchar(12) NOT NULL (first 8 chars for identification)
       - createdAt: timestamp with timezone, defaultNow()
       - lastUsedAt: timestamp with timezone, nullable
       - expiresAt: timestamp with timezone, nullable
       - revoked: boolean NOT NULL default false

    2. Add auth and webhooks sections to configSchema in server/config/schema.ts:
       ```
       auth: z.object({ enabled: z.boolean().default(false) }).default(...)
       webhooks: z.object({
         url: z.string().url().optional(),
         secret: z.string().optional(),
         timeout_ms: z.number().int().default(10000),
         max_retries: z.number().int().default(3),
       }).default(...)
       ```
       Use the pre-parsed default pattern (parse sub-schema first, use result as .default()) per Phase 01-01 decision.

    3. Create server/auth/auth-service.ts:
       - Uses node:crypto randomBytes(32) for key generation with "df_" prefix
       - Uses scryptSync for hashing (HASH_LEN=64), timingSafeEqual for comparison
       - Injectable db parameter (Database type from server/db/index.ts)
       - Methods: generateKey(), createKey(name), validateKey(rawKey), listKeys(), revokeKey(id)
       - validateKey also updates lastUsedAt timestamp

    4. Write tests in server/auth/__tests__/auth-service.test.ts:
       - Mock the database with inline stubs (no real DB)
       - Test all behaviors listed above
       - Verify timing-safe comparison is used (by testing with valid/invalid keys)
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Auth plugin, key admin routes, and route protection wiring</name>
  <files>
    server/auth/auth-plugin.ts,

  <behavior>
    - When auth.enabled=true, requests without Bearer token to /api/jobs get 401
    - When auth.enabled=true, requests with valid Bearer token to /api/jobs get 200
    - When auth.enabled=false, requests without Bearer token to /api/jobs pass through
    - GET /api/health always returns 200 regardless of auth state
    - WebSocket upgrade at /ws/jobs/:id with ?token=validKey succeeds
    - WebSocket upgrade at /ws/jobs/:id without token gets rejected when auth enabled
    - POST /api/admin/keys with {name} creates key and returns raw key
    - GET /api/admin/keys returns list without hashes
    - DELETE /api/admin/keys/:id revokes key
    - Admin key routes require auth when auth.enabled=true
  </behavior>
  <action>
    1. Create server/auth/auth-plugin.ts as a Fastify plugin (fp wrapper):
       - Dependencies: ['config', 'db']
       - Creates AuthService instance with fastify.db
       - Decorates fastify with 'authService'
       - Registers @fastify/bearer-auth with addHook:false and custom auth function that calls authService.validateKey()
       - errorResponse returns RFC 7807 format with application/problem+json content type
       - If config.auth.enabled is false, register plugin but skip bearer-auth registration (just decorate authService for key management)

    2. Create server/auth/key-routes.ts:
       - POST /admin/keys: accepts { name, expiresAt? }, calls authService.createKey(), returns 201 with { id, name, rawKey, prefix, createdAt }
       - GET /admin/keys: calls authService.listKeys(), returns array
       - DELETE /admin/keys/:id: calls authService.revokeKey(id), returns 204

    3. Modify server/api/plugin.ts to add auth protection:
       - Add 'auth' to dependencies array
       - Create a protected scope with addHook('onRequest', fastify.verifyBearerAuth) when auth is enabled
       - Register jobRoutes, deviceRoutes, configRoute inside protected scope
       - Keep healthRoute OUTSIDE protected scope (public)
       - Register keyRoutes inside protected scope under /api prefix
       - For WebSocket routes: they live in websocket-plugin.ts, NOT in api plugin. Add a preHandler to the WS routes in websocket-plugin.ts that checks query param ?token when auth.enabled. Use fastify.authService.validateKey(token) directly. If invalid, close socket with 1008 (Policy Violation).

       IMPORTANT: The WS routes are in websocket-plugin.ts which registers BEFORE auth-plugin. To handle this, add the WS auth check in the api-plugin's onReady hook, or restructure: register auth-plugin BEFORE websocket-plugin in server/index.ts, then in websocket-plugin check if fastify.authService exists and validate.

    4. Update server/index.ts plugin registration order:
       - Add auth-plugin import
       - Register auth-plugin AFTER db plugin but BEFORE websocket-plugin (so authService is available)
       - Order: config -> pool -> db -> auth -> websocket -> artifact -> job -> lifecycle -> api -> static

    5. Write tests in server/auth/__tests__/auth-plugin.test.ts:
       - Use Fastify test instance with mock plugins
       - Test route protection with/without Bearer token
       - Test auth.enabled=false bypass
       - Test health endpoint remains public
       - Test admin key CRUD routes

Server WebSocket protocol (from server/streaming/types.ts):
```typescript
// Messages sent over /ws/jobs/:id
{ type: 'log', data: { line: string, stream: 'stdout'|'stderr' }, timestamp: string }
{ type: 'step', data: { flowName: string, command: string|null, status: string, durationMs: number|null }, timestamp: string }
{ type: 'status', data: { status: 'running'|'passed'|'failed'|'cancelled'|'timeout' }, timestamp: string }
{ type: 'metrics', data: { totalPss: number, nativeHeap: number, javaHeap: number }, timestamp: string }
{ type: 'logcat', data: { line: string }, timestamp: string }
```

Server late-join: Ring buffer replays up to 200 messages on WebSocket connect.

Server POST /api/jobs:
- Multipart: files (YAML), platform (field), metadata (JSON string field)
- Returns 201 with job object including id field

  <name>Task 1: WebSocket streaming infrastructure</name>

  <action>
    1. Create `cli/internal/streaming/types.go`:
       - WsMessageType string constants: MsgLog, MsgStep, MsgMetrics, MsgStatus, MsgLogcat
       - JobMessage struct: Type WsMessageType, Data json.RawMessage, Timestamp string
       - LogData struct: Line, Stream string
       - StepData struct: FlowName string, Command *string, Status string, DurationMs *int
       - StatusData struct: Status string
       - LogcatData struct: Line string
       - MetricsData struct: TotalPss, NativeHeap, JavaHeap int
       - JobSummary struct: Passed, Failed, Skipped, Total int; Duration time.Duration; DeviceName string; FailedFlows []FailedFlow
       - FailedFlow struct: FlowName, FailingStep string

    2. Create `cli/internal/streaming/ws.go`:
       - StreamJob(ctx context.Context, wsURL string, handler MessageHandler) (exitCode int, summary *JobSummary, err error)
       - Uses coder/websocket: Dial with ctx, read loop, parse JobMessage, dispatch to handler
       - On StatusData with terminal status (passed/failed/cancelled/timeout): break loop, compute exit code
       - Handle context cancellation (Ctrl+C): close websocket with StatusNormalClosure, return current summary
       - Reconnect NOT implemented in v1 -- rely on server late-join replay if user re-runs
       - MessageHandler interface: HandleLog(LogData), HandleStep(StepData), HandleStatus(StatusData), HandleMetrics(MetricsData)

    3. Create `cli/internal/streaming/renderer.go`:
       - Renderer struct: isTTY bool, writer io.Writer, currentFlowName string, completedSteps []StepData, startTime time.Time, summary *JobSummary
       - Implements MessageHandler interface
       - HandleStep: If TTY, use ANSI escape (\033[1A\033[2K) to update current step in-place. Completed steps (status != "running") stay printed above. Non-TTY: append each step as `[STATUS] flow: command` line.
       - HandleLog: Print log line with optional stream prefix in non-TTY
       - HandleStatus: Record final status, compute duration
       - HandleMetrics: Ignored in v1 (metrics display is Web UI concern)
       - Track FailedFlows: when a step has status "failed", record flow+command
       - NewRenderer(w io.Writer, isTTY bool) *Renderer

    4. Create `cli/internal/streaming/summary.go`:
       - PrintSummary(w io.Writer, s *JobSummary, isTTY bool)
       - Format: blank line, horizontal rule (---), then:
         ```
         Results: 5 passed, 1 failed, 0 skipped (12.3s)
         Device: pixel_6_api34

         Failed:
           X login-flow > Tap on "Submit"
           X checkout-flow > Assert "Order confirmed" visible
         ```
       - Use StatusColor for pass/fail coloring, StatusSymbol for X marks
       - Non-TTY: same layout without colors

    5. Create `cli/internal/streaming/ws_test.go`:
       - TestParseLogMessage: unmarshal JSON into JobMessage, extract LogData
       - TestParseStepMessage: unmarshal step JSON, verify fields
       - TestParseStatusMessage: unmarshal status, verify terminal detection
       - TestSummaryOutput: create JobSummary, call PrintSummary, verify output contains expected pass/fail counts
       - Use bytes.Buffer as writer for output capture
  </action>

  <action>
    1. Create `cli/internal/client/submit.go` (separate file from jobs.go to avoid conflict with Plan 02):
       - CreateJob(ctx context.Context, files []string, platform string, metadata map[string]string) (*Job, error)
       - Build multipart body: for each file path, open and add as form file part with filename = filepath.Base
       - Add "platform" field
       - Add "metadata" field as JSON string if non-empty
       - Set Content-Type to writer.FormDataContentType() (critical -- includes boundary)
       - POST to /api/jobs, expect 201, decode response into Job struct
       - Import Job type from types.go (created by Plan 02, or define locally if Plan 03 runs first -- but since both are wave 2 depending on 01+04, types.go will exist from Plan 02 Task 1)

    2. Create `cli/cmd/run.go`:
       - `run` command, takes one or more YAML file paths as args (cobra.MinimumNArgs(1))
       - Flags: --platform (string, resolved via config), --async (bool), --timeout (int, seconds), --meta (string slice, key=value pairs)
       - Validate all file paths exist and end in .yaml/.yml before upload
       - Parse --meta flags into map[string]string (split on first "=")
       - Create client, call CreateJob with files, platform, metadata
       - If --async: print job ID and exit 0. In --json mode: output {"jobId": "..."}.
       - If not --async (default):
         a. Print "Job {id} created, connecting..."
         b. Build WebSocket URL: replace http(s):// with ws(s):// in server URL, append /ws/jobs/{id}
         c. Set up signal handling: trap SIGINT/SIGTERM, cancel context on first signal, force exit on second
         d. Create Renderer, call streaming.StreamJob
         e. Print summary via PrintSummary
         f. Return ExitError with appropriate code (0=passed, 1=failed, 2=error)
       - Register on rootCmd in init()

    3. Create `cli/cmd/logs.go`:
       - `logs` command, takes job-id as first arg (cobra.ExactArgs(1))
       - Flag: --follow (bool, -f shorthand)
       - Without --follow:
         a. Create client, call GetJobLogs(ctx, jobID) -- uses GetJobLogs from jobs.go (created by Plan 02)
         b. Print raw log text to stdout
         c. In --json mode: output {"logs": "..."}
       - With --follow:
         a. Build WebSocket URL for /ws/jobs/{id}
         b. Create a simple log-only handler that prints LogData lines (no step rendering)
         c. Call streaming.StreamJob with log handler
         d. Auto-exit when status message indicates terminal state
         e. Print summary and exit with appropriate code
         f. Signal handling same as run command
       - Register on rootCmd in init()

    Key implementation details per user decisions:
    - Exit codes: 0 = all passed, 1 = test failures, 2 = infrastructure/CLI error
    - TTY mode: inline step updates via ANSI escapes; non-TTY: log-style append
    - `logs --follow` auto-exits with summary when job completes
    - Ctrl+C: first signal cancels gracefully (print summary), second force-exits
    - Environment variables: DEVICE_FARM_URL, DEVICE_FARM_API_KEY, DEVICE_FARM_PLATFORM all resolved via config.Resolve*

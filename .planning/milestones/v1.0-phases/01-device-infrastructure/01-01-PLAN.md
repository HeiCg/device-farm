    1. Initialize project: Create package.json with name "device-farm", type "module" (ESM). Install dependencies:
       `npm install fastify fastify-plugin zod js-yaml drizzle-orm postgres async-mutex`
       `npm install -D drizzle-kit vitest pino-pretty @types/js-yaml typescript tsx @types/node`

    2. Create tsconfig.json: target ES2022, module NodeNext, moduleResolution NodeNext, strict true, outDir dist, rootDir ., include ["server/**/*"]. Paths alias if needed.

    3. Create vitest.config.ts: import from vitest/config, set include to ["server/**/__tests__/**/*.test.ts"], globals false.

    4. Create server/types/index.ts: Export Platform type ('android' | 'ios'), DeviceState enum (Booting, Idle, Allocated, Running, Cleanup, Error, Offline), DeviceInfo interface (id, name, platform, state, emulatorId, port, pid, currentJobId), and VALID_TRANSITIONS map as shown in RESEARCH.md.

    5. Create server/config/schema.ts: Zod schema matching implementation-plan.md config.yaml structure exactly. Include server (port, host), pool (max_devices, android config, ios config), storage (recordings, logs), jobs (timeout, queue size, cleanup), job_metadata_schema (required, optional). Export configSchema and AppConfig type. Add database_url field (z.string().default('postgresql://localhost:5432/device_farm')).

Applies env overrides (DEVICE_FARM_PORT -> server.port, DATABASE_URL -> database_url). Runs configSchema.safeParse(). On failure, formats error with field paths. Returns typed AppConfig.

    7. Create server/config/plugin.ts: Fastify plugin using fastify-plugin. Calls loadConfig(), decorates fastify instance with 'config'. Augment FastifyInstance type declaration.

    8. Create config.yaml: Default config file matching the schema with sensible defaults (matching implementation-plan.md example).

    9. Write tests in server/config/__tests__/loader.test.ts covering the behaviors listed above. Use vi.stubEnv() for env var tests. Create temp YAML files for test cases.

       - Include jobs, job_files, job_steps, recordings tables from implementation-plan.md as well (they will be used in Phase 2 but defining schema now avoids migration conflicts later).

On missing, collects error with install hint. Throws if any missing.
